After the 30× gate: what to speed up, and what to add

Every change must keep output bit-identical to sarek 3.10.0 / GATK 4.6.2.0 at all stage boundaries. The levers below are ranked by exact speed gain against proof burden; the scope list is what stands between real users' data and the pipeline.

Update 2026-10-13. A 36-hour iteration run landed levers 1, 3 and 5, GPU mate rescue, poly-G trimming and multi-lane input. The 30× genome went from 2 h 47 min to 2 h 08 min, still identical (41/41). The live record is the iteration board on the stack map.

Exact speed levers, ranked

1

PairHMM computes each shared haplotype prefix once

landed
Stage HaplotypeCallerGain PairHMM 2.28×; HC −18 % on the chr20 sliceRisk gated
  • GATK 4.6.2.0 has prefix-reuse code (hapStartIndex) that never runs: every haplotype is recomputed from column 1.
  • For haplotypes of equal length, columns of a shared prefix and the running final sum up to it are bit-identical, so computing them once is exact. 59 % of all cells in our PairHMM dump fall in such prefixes.
  • Landed 2026-10-11: lanes over 8 reads, a sorted haplotype traversal with saved columns at branch points. PairHMM 1.90×10¹⁰ → 4.33×10¹⁰ cells/s on 20 threads, bitwise identical on 639,220 pairs and on GATK's own likelihood oracle (993 regions). Gates 18/18; HaplotypeCaller on the 30× chr20 slice 121 → 99 s. The rest of HaplotypeCaller (assembly, traversal) now sets its pace.
2

Mate rescue: prune and band the alignment exactly

next
Stage alignmentGain est. 20–30 % of WGS alignmentRisk medium-high
  • bwa-mem3's approach: exact 5-mer hits between mate and window bound the best possible score; only rows that can reach the threshold are computed, in diagonal bands.
  • Our rescue windows are ~1,339 rows for a 151 bp mate, so most cells cannot matter.
  • The proof must reproduce bwa's second-best score bookkeeping, which bwa-mem2's batched kernels got wrong (XS ±1–4, MAPQ ±2–18), and the start-recovery pass. Gate every call on the 62k and 70k dumps first.
3

Run HaplotypeCaller's interval groups concurrently

landed
Stage HaplotypeCallerGain ~10 %Risk low
  • sarek's 21 groups each start with fresh random-number state, so they are independent. Threads are ~91 % busy today; the win is in the tails.
4

Small certified alignment shortcuts

later
Stage alignmentGain 5–10 % combinedRisk low
  • Repeat-job reuse in rescue, skipping provably no-op dedups, memoized gap limits, an index for the containment sweep, a certified band for the final CIGAR.
5

Chaining with a denser suffix array

landed
Stage alignmentGain chaining 22 → ~10 µs/readRisk low once unblocked
  • Landed 2026-10-13 at interval 2 (22 GB index): chaining on the 30× chunk 42 → 27.5 µs per record, chunk alignment 430 → 414.5 s, identical output. Interval 1 ran without the old CUDA error, but was slower overall at a 77.5 GB peak.

Scope beyond the 18 gates

Our BAMs and VCF equal sarek's, so any tool run unmodified on them gives sarek's result; porting one only buys speed. Each item below needs a new sarek golden first.

ItemEffortWhy
Poly-G trimming (NovaSeq, NextSeq) landedS–Mfastp enables it from instrument read names; our prep refuses such input, so most users' own FASTQs fail today.
Multiple lanes and read groups, optical duplicates landedMThe read group is hard-coded to one lane; Picard's optical-duplicate count is never computed.
BAM and CRAM indexesS–MAlready a stated, unproduced gate; every viewer needs one.
CRAM output, record-identicalMsarek's default output format; byte-exact would need htslib's codec choices.
QC files: samtools stats, mosdepth, bcftools stats, vcftools, FastQC dataMOn by default in sarek, deterministic, cheap to gate.
GVCF output, then single-sample GenotypeGVCFsL + MCohorts and reanalysis. New: reference-confidence blocks, <NON_REF>, physical phasing.
Other references: no-BED intervals, BQSR skip, ALT contigsMGRCh37, T2T, GRCh38 with .alt.
Mutect2 tumor–normalL+A separate track that reuses assembly and PairHMM.

Not worth porting: DeepVariant, the CNN variant filter, VEP and snpEff. Run them on our outputs as they are.

Order of work after the 30× gate

  1. Shared-prefix PairHMM (landed); next on HaplotypeCaller: assembly and the per-group tails.
  2. Poly-G trimming and multi-lane / read-group support.
  3. Exact mate-rescue pruning.
  4. Indexes, CRAM and the QC files.
  5. GVCF output.
