### 0.4 Traversal skeleton **[source]**

`HaplotypeCaller extends AssemblyRegionWalker` (`tools/walkers/haplotypecaller/HaplotypeCaller.java`). `AssemblyRegionWalker.onStartup` (`engine/AssemblyRegionWalker.java` L77-88) builds one `MultiIntervalLocalReadShard` **per contig** from the user intervals, padded by `assemblyRegionPadding = 100` (`makeReadShards` L99-108). `traverse()` (L156-176) attaches, per shard, the pre-filter transformer, the counting read filter, the downsampler and the post-filter transformer, then `processReadShard` (L186-210) iterates an `AssemblyRegionIterator` and calls `apply(region, …)` per region, which is `hcEngine.callRegion(region, featureContext, referenceContext).forEach(vcfWriter::add)` (`HaplotypeCaller.java` L283-285). Everything is single-threaded and strictly sequential: contig order of the dictionary, then regions in genomic order, then records in the order `callRegion` returns them (7.9).

### 1.1 Interval list **[source]**

* `--intervals x.bed` is loaded through `IntervalUtils.parseIntervalArguments` (`utils/IntervalUtils.java` L306-344): a Feature file ⇒ `featureFileToIntervals` (L354-364) ⇒ htsjdk `BEDCodec.decode` (`tribble/bed/BEDCodec.java` L~96-120) with `StartOffset.ONE`: start = `tokens[1] + 1`, end = `tokens[2]`. * `loadIntervals` (L229-249): no padding (`--interval-padding 0`), set rule UNION, then `sortAndMergeIntervals(…, IntervalMergingRule.ALL)` (L464-473): sort by `GenomeLoc` (contig index in the **reads' sequence dictionary**, then start, then stop), then `mergeIntervalLocations` (L964-985) merges overlapping intervals **and adjacent ones** (`contiguousP` = `!discontinuousP`, `GenomeLoc.java` L114-116: `(start-1) > that.stop || (that.start-1) > this.stop` false ⇒ contiguous; rule `ALL` merges those). The log `Processing 49311641 bp` equals the raw BED sum, so the Agilent BED has no overlapping/adjacent rows **[source: computed]**.
* Per shard (`MultiIntervalLocalReadShard` L48-62): `intervals` = the contig's intervals re-passed through `getIntervalsWithFlanks(…, 0)` (sort + merge again); `paddedIntervals` = each interval expanded by 100 on both sides (`GenomeLocParser.createPaddedGenomeLoc` L459-464, clipped to the contig), then sorted and merged with rule ALL (L1000-1008 `getIntervalsWithFlanks`). Reads are fetched for the padded set; activity is evaluated only on the unpadded set (2.1).

### 1.6 Assignment of reads to regions **[source]**

`AssemblyRegionIterator` (`engine/AssemblyRegionIterator.java`) wraps the shard's read iterator in a `ReadCachingIterator` (L39) that is drained by a `LocusIteratorByState` (L43, `DownsamplingMethod.NONE`, `includeReadsWithDeletionAtLoci = true`) to produce pileups for the activity profile (2.1). When a region is emitted, `fillNextAssemblyRegionWithReads` (L103-122) adds, in this order: (a) every read of the **previous** region that overlaps the new region's padded span, then (b) cached reads in stream order up to the first read that starts after the padded span (`IntervalUtils.isAfter`: contig later, or `start > paddedEnd`), keeping those that overlap the padded span. A read overlapping two consecutive regions' padded spans is therefore a member of both; `AssemblyRegion.add` (L287-300) requires non-decreasing starts, which the two-source order satisfies. The region's read list is the post-filter, post-downsampling stream.

## 2. Active-region determination

### 2.1 Per-locus pileups **[source]**

`LocusIteratorByState.lazyLoadNextAlignmentContext` (`utils/locusiterator/LocusIteratorByState.java` L285-326) emits one `AlignmentContext` per reference position covered by at least one read with a non-`N`, non-skipped element, over the loci of the shard's **unpadded** intervals (`IntervalLocusIterator`/`IntervalAlignmentContextIterator`, `AssemblyRegionIterator` L44-45). A read contributes a `PileupElement` at a locus when the `AlignmentStateMachine` (`utils/locusiterator/AlignmentStateMachine.java` `stepForwardOnGenome` L225-297) is on an `M/=/X` base or inside a `D` (deletions are included: `includeReadsWithDeletionAtLoci = true`), **except** when `ReadUtils.isBaseInsideAdaptor(read, pos)` (L311, L337-339; `utils/read/ReadUtils.java` L1066-1072): with `adaptorBoundary = getAdaptorBoundary(read)` (L527-536: `CANNOT_COMPUTE` unless `hasWellDefinedFragmentSize` L547-572: paired, mate mapped, TLEN ≠ 0, opposite strands, and for reverse `end > mateStart`, for forward `start <= mateStart + TLEN`; else reverse ⇒ `mateStart - 1`, forward ⇒ `start + |TLEN|`), the base is excluded iff `adaptorBoundary != CANNOT_COMPUTE && read.getFragmentLength() <= 100` (note: the **signed** TLEN compared with `DEFAULT_ADAPTOR_SIZE = 100`, so reverse-strand reads with negative TLEN always pass this test) and (`reverse ? pos <= boundary : pos >= boundary`).
Insertions never create elements; soft clips never create elements.

`isActive` (`HaplotypeCallerEngine.java` L662-725) receives the pileup; `context.getBasePileup().isEmpty()` ⇒ probability 0 (L669-672). `IntervalAlignmentContextIterator.next()` (`utils/locusiterator/IntervalAlignmentContextIterator.java` L~20-45) walks **every** locus of the shard's unpadded intervals (`IntervalLocusIterator`) and returns the LIBS context when it overlaps the locus, otherwise an **empty** `AlignmentContext` (`createEmptyAlignmentContext`), so `isActive` runs once per interval base, contexts are contiguous within an interval (`ActivityProfile.add` L72-73 asserts this), and the profile is force-converted at every gap between intervals (2.4). Note the asymmetry at interval edges: reads overlapping an interval contribute pileup elements only at loci inside the interval, but reads are *fetched* for the 100-padded intervals (1.2), so a read entirely inside the padding is never seen by `isActive` yet is a region member.

### 2.2 The ref-vs-any likelihood model **[source]**

`ReferenceConfidenceModel.calcGenotypeLikelihoodsOfRefVsAny(ploidy=2, pileup, refBase, minBaseQual=10, hqSoftClips, readsWereRealigned=false)` (`tools/walkers/haplotypecaller/ReferenceConfidenceModel.java` L399-436):

* `likelihoodCount = 3`, `log10Ploidy = log10(2)`.
* For each element `p`: `qual = p.isDeletion() ? refModelDeletionQuality (30, `--reference-model-deletion-quality`) : p.getQual()`; skip if `qual <= 10` **and** the element is not a deletion (L417; deletions with qual 30 never skip).
* `isAlt = isAltBeforeAssembly(p, refBase)` (L502-505): `base != refBase || isDeletion || isBeforeDeletionStart || isAfterDeletionEnd || isBeforeInsertion || isAfterInsertion || isNextToSoftClip`, where (`utils/pileup/PileupElement.java`): `isBeforeDeletionStart` = not a deletion, `offsetInCurrentCigar == len-1`, and the next on-genome element (`M/=/X/D`, skipping `I/S/H/P/N`) is `D` (L112-114); `isAfterDeletionEnd` symmetric with the previous on-genome element (L125-127); `isBeforeInsertion`/`isAfterInsertion`/`isNextToSoftClip` test the **immediately adjacent** CIGAR element (`getAdjacentOperator`, L466-476, L433-460), so an `I` or `S` separated by a `D` does not count.
* Per element (L473-500): `isAlt ? (nonRef = qualToProbLog10(q), ref = qualToErrorProbLog10(q) + LOG10_ONE_THIRD) : (ref = qualToProbLog10(q), nonRef = qualToErrorProbLog10(q) + LOG10_ONE_THIRD)`; `gl[0] += ref + log10(2)`, `gl[2] += nonRef + log10(2)`, `gl[1] += approximateLog10SumLog10(ref + log10(1), nonRef + log10(1))` (loop L491-496 with `i = 1, j = 1`). `qualToProbLog10(byte)` is a table `log10(1 - 10^(-q/10))` (`utils/QualityUtils.java` L52-57, L114-116); `qualToErrorProbLog10(byte q) = (q & 0xff) * -0.1` (L174-176, L188-191); `LOG10_ONE_THIRD = -log10(3.0)` (`utils/MathUtils.java` L30).

## 10. Randomness, threads, run-to-run identity

* The only RNG is `Utils.getRandomGenerator()` (1.5), consumed by (a) `ReservoirDownsampler.submit` and (b) `QualByDepth.fixTooHighQD`. Both are called from the single traversal thread in a deterministic order, so the output is reproducible but **history-dependent**: a port must consume the same draws in the same order (reads beyond the 50th at each start position, in BAM order, interleaved with QD jitters of records emitted by earlier regions — note that the downsampler runs *ahead* of calling by up to the activity-profile look-ahead, 2.4, so draw interleaving follows the lazy iterator, not genomic order of records). Tier0 shows zero downsampling draws; tier1 desynchronizes after chr1:~147 Mb (13.x gives the exact record).
* `--native-pair-hmm-threads 2` is inert (Java HMM). No other parallelism (no Spark, `AsyncVariantContextWriter` is not used; `USE_ASYNC_IO_WRITE_FOR_SAMTOOLS=true` only affects BAM writing, none here).
* Identity hash codes of graph vertices (4.5) and `HashSet`/`HashMap` iteration over them never reach the output; r1 vs r2 records are byte-identical at both tiers (`docs/REFERENCE-VARIABILITY.md`; re-verified: body md5 `0448b2f7…` tier1 r1 = r2, `498196ef…` tier0 r1 = r2).
* Wall-clock dependence: only the `Date=` of `##GATKCommandLine`.

## 11. Floating-point inventory (every FP operation that can change output)

All Java arithmetic is strict IEEE-754 double (JDK 17: `strictfp` everywhere; no FMA contraction, no extended precision). Rust must not re-associate or fuse. `Math.log/log10/exp/pow/log1p/expm1/sqrt` may be HotSpot intrinsics that differ from `StrictMath` (fdlibm) in the last ulp on some platforms; **measured in the reference container's JVM** (`community.wave.seqera.io/library/gatk4_htslib_samtools:6fd46722be032bdd`, OpenJDK 17.0.17-internal, aarch64, C2 warmed up): 0 mismatches in 5×10⁶ samples per function for `log(p∈(0,1))`, `log10(x∈(0,1000))`, `exp(x∈(-40,0))`, `pow(10, x∈(-40,0))`, `pow(10, q/-10)`, `log1p(-p)`, `expm1(x<0)`, `sqrt` **[source: `LibmCheck.java`, 12]**. So an **fdlibm-exact** implementation (JDK `StrictMath` semantics; the Rust `libm` crate derives from fdlibm/musl — verify it against JDK `StrictMath` vectors, not glibc) reproduces every transcendental here; `java.util.Random.nextGaussian` uses `StrictMath` by definition. ### 13.1 Riskiest exactness traps (summary)

1. The shared `java.util.Random(47382911)`: reservoir `nextInt` draws and QD `nextGaussian` jitter interleave in iterator order (downsampler runs ahead of calling).
2. PL rounding before the AF calculation (activity model and genotyping both operate on `PL/-10`), and `GQ` = integer PL gap.
3. `approximateLog10SumLog10` Jacobian table (10⁴ steps) everywhere log-sums appear, including inside the PairHMM transition table.
4. PairHMM in double with `2^1020` scaling, per-pair full recompute (`recacheReadValues` always true), `/3.0` tristate priors, `N` handling, PCR-model indel quals, MAPQ cap and the 18→6 base-quality squash.
5. Haplotype order: k-best (score desc, bases desc) then **re-sorted by length/base string after trimming**; `KBestHaplotype.isReference` is never true.
6. Java SW asymmetries (`>=` diagonal, last-column `>=`, bottom-row `>` with diagonal-distance tie-break), the exact-substring shortcut, `NNNNNNNNNN` padding, `CigarBuilder` deletion rules, left-alignment.
7. Seq-graph simplification changes edge multiplicities (`makeOREdge(…,1)`), hence path scores and order; and the pruning multiplicity of a read-threaded edge equals its total multiplicity (min-heap of `{1, current}` polled once), not a per-sample minimum.
8. Dangling-head recovery uses the **legacy** prefix match (`minMatchingBases = -1`), reversed strings, `max(1, len/kmer)` mismatches.
9. Read clipping chain order and the overlap-pair quality adjustment (`min(q,20)` / 0, index arithmetic ignoring indels), applied to the original reads before assembly and PairHMM.
10. Annotations use **realigned** reads; filtered reads re-enter with likelihood 0 (count in DP and MQ, not AD).
11. Rank-sum ranks and sums in `float`, exact permutation test below n=10 with commons-math `erfInv`; Fisher via commons-math hypergeometric log-probabilities.
12. Formatting: Java `%.Nf` HALF_UP, `formatVCFDouble` thresholds, QUAL `.00` trimming, alphabetical INFO, `GQ` cap at write time.
13. Pileup adaptor exclusion uses the signed TLEN vs 100; soft-clip reversion depends on `hasWellDefinedFragmentSize`.
14. Transcendentals must be fdlibm-exact (`StrictMath`): verified that the container JVM's `Math` intrinsics agree with `StrictMath` on aarch64 (11), so a fdlibm port suffices, but glibc's `log10`/`pow` do not; dump the tables from the JVM and compare bit-for-bit.
